# Архитектура для трёх независимых участников

## Почему именно так

Для 24 часов нужен один репозиторий с тремя изолированными приложениями и одним небольшим набором контрактов. Отдельный процесс ML позволяет norerade менять провайдер и оценщик без изменений серверного расчёта. SQLite достаточно для локального демонстрационного потока. Redis, Celery, Kubernetes, общая Python-библиотека на все сервисы и общие UI/runtime пакеты сейчас увеличили бы пересечения между людьми.

```text
EVA/
  frontend/          Mansur: UI, API adapter, собственные dependencies/tests
  backend/           Chach: HTTP, persistence, imports, deterministic scoring
  ml/                norerade: inference, prompts, evidence, quality evaluation
  contracts/         Общие файлы: schemas + synthetic examples
  docs/              Общие файлы: требования, план, правила, skills
  tools/             Общие файлы: локальные проверки контрактов/границ
  AGENTS.md          Общие обязательные правила
```

## Границы модулей

| Зона | Владеет | Не делает |
|---|---|---|
| Frontend | Списки, карточка диалога, конфиг чек-листа, доказательства, appeal/review UI, клиент HTTP | Не вызывает модель напрямую; не рассчитывает канонический итог; не читает SQLite |
| Backend | Импорт/нормализация, версии чек-листа, оркестрация ML, валидация, scoring, хранение, апелляции | Не угадывает языковые выводы; не меняет промпты ML; не правит UI |
| ML | Настраиваемая интерпретация критериев, RU/KZ/EN, цитатные ссылки, uncertainty, оценка качества/стоимости | Не меняет баллы по формуле, не пишет в бизнес-БД, не принимает апелляции |

У Backend и ML собственные окружения Python; у Frontend собственный package-lock. Никаких прямых импортов `backend` из `ml` и наоборот. Общие схемы читаются как данные; небольшой локальный загрузчик схем допустимо повторить, чтобы не создавать совместно редактируемый runtime-модуль.

## Поток оценки

1. Backend сохраняет нормализованный разговор и стабильные ID реплик. Начальный каркас читает синтетический fixture.
2. Пользователь выбирает ID и конкретную версию чек-листа. В будущем запуск фиксирует снимок разговора и чек-листа.
3. Backend передаёт ML только `evaluation-request`; сервис не получает права на БД и GitHub.
4. ML возвращает решения, объяснения и существующие ID доказательств. Контекст клиента не может становиться инструкцией для модели. Пока провайдер не выбран, все критерии имеют `needs_review`.
5. Backend валидирует схему и связи, проверяет типы ответов, шкалы, разрешённость N/A и completeness. Невалидный результат не превращается в успешный.
6. Backend детерминированно рассчитывает итог и секции, сохраняет исходный ответ и результат расчёта в SQLite. Чистая функция scoring используется повторно после решений по апелляциям.
7. UI показывает статус, источник результата, итог и evidence-навигацию. Ошибка ML и отсутствие результата явно видны.

Сейчас вызов синхронный с ограниченным timeout; 65 диалогов не требуют инфраструктуры очередей. После подключения модели — ограниченная параллельность и прогресс серии запусков. Повторы только ограниченные и учитываемые в стоимости; не делать бесконечные retry.

## Дальнейшее хранение и апелляции — проектирование, ещё не реализация

| Сущность | Ключевые поля и инвариант |
|---|---|
| Conversation | ID, исходный и нормализованный transcript, language/channel, source_group, audio_url, content hash |
| ChecklistVersion | `(checklist_id, version)`, immutable JSON, created_at; новая правка создаёт новую версию |
| Evaluation | ID, conversation snapshot/hash, checklist snapshot/version, model metadata, original response, original score, created_at |
| Appeal | ID, evaluation_id, criterion_id, comment, status, created_at; критерий должен принадлежать оценке |
| ReviewDecision | ID, appeal_id, reviewer label, original value, decision/value, reason, evidence, created_at; append-only |
| FinalResult | Проекция исходных решений с принятыми overrides + пересчёт; revision для конкурентных решений |

Старую оценку не перезаписывать при апелляции. Подтверждение оставляет значение, изменение требует валидного нового значения, доказательства и причины. Финальный результат вычисляется с **той версией чек-листа**, по которой получена исходная оценка. Нужны транзакция и optimistic concurrency (`expected_revision`, конфликт 409), чтобы два проверяющих не теряли решения друг друга. Наличие UI-действия «Проверяющий» для демо не является авторизацией для production.

Следующие API-сценарии согласуются общими схемами до реализации: импорт набора; создание новой версии чек-листа; создание апелляции; принятие решения с revision; чтение карточки с original/decisions/final. Endpoint-имена пока намеренно не закреплены как существующие.

## Корректность консультаций и качество ML

Модель не должна выдумывать брокерские правила, тарифы или факт выполненного защищённого действия. Для содержательной проверки нужны подтверждённые материалы организаторов/база знаний; при нехватке основания — `needs_review`. Доказательство оценивается отдельно: существует ли реплика, поддерживает ли вывод, корректен ли проверенный участок для пропуска.

Метрики: agreement/F1 по каждому boolean/flag, accuracy и MAE для шкал, качество N/A, валидность ссылок на реплики, доля `needs_review`, задержка и суммарная стоимость. Срезы RU/KZ/EN и chat/call обязательны. DEV маленький: не выдавать метрики на тех же примерах, на которых подбирался промпт, за независимую проверку. Контрольный набор не использовать для донастройки под правильные ответы.

## Встраивание и переносимость

Frontend строится в статические HTML/CSS/JS, API-адрес конфигурируемый. Стили и события ограничиваются корнем приложения, без зависимости от внешней навигации host-страницы. Dynamics 365 — будущий адаптер, сейчас SDK и учётные записи не требуются.

Сервисы слушают loopback, CORS ограничен локальным Frontend. Для совместного публичного доступа потребуется отдельная задача: авторизация, доступ к аудио, CORS origin, хранение секретов, retention и ограничения импорта. Эти функции не имитируются в каркасе.
