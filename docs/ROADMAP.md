# План параллельной работы на 24 часа

Отсчёт от фактического старта хакатона. Интервалы ниже — предлагаемый план, не расписание организаторов. Начальный каркас уже создан; главное — довести обязательный сквозной сценарий до первого работающего состояния рано.

| Период | Mansur · Frontend | Chach · Backend | Kroud · ML | Общий критерий готовности |
|---|---|---|---|---|
| 0–2 ч | Запуск demo, изучение adapter/types | Запуск API/scoring, проверка SQLite | Запуск stub, схема результата | Каждый запускает свою часть; полный стенд возвращает честный pending |
| 2–5 ч | Список/выбор диалогов, карточка, loading/error | Адаптер DEV, нормализация и сохранение данных | Один провайдер, structured output, generic evaluator | Один диалог проходит от импорта до проверенной оценки |
| 5–8 ч | Критерии, объяснения, переход к реплике, N/A | Версии чек-листа, устойчивое хранение снимков | RU/KZ/EN, evidence validators, пропуски/N/A | По одному осмысленному примеру каждого языка и канала |
| 8–12 ч | Форма апелляции и режим проверяющего | Append-only решения, транзакция, пересчёт | Проверка ошибок модели, локальные human labels | Исходная оценка сохраняется; решение меняет финальную |
| 12–16 ч | Редактор типа/веса/N/A/шкалы критерия | Валидация/создание новых версий | Новый произвольный критерий без if по ID | Замена критерия через UI без изменения кода |
| 16–20 ч | Полировка навигации, empty/error, аудио | Batch/progress, таймауты, лимиты, restart | Срезы качества, стоимость, retry budget | Набор обрабатывается предсказуемо; ошибки видны |
| 20–23 ч | Репетиция показа | Интеграционная проверка и README | Зафиксировать provider/model/prompt config | Сквозной сценарий полностью воспроизводим |
| 23–24 ч | Показ результатов контрольного набора | Получение/запуск контроля, сохранение | Проверка корректности формата без подгонки по ответам | Люди фиксируют версию и готовят пятиминутный показ |

## Первая задача каждого

**Mansur:** вывести реальную карточку через HTTP adapter и обработать `needs_review`, ошибку API и N/A разными состояниями. Затем добавить UI редактирования чек-листа после согласования endpoint-контракта.

**Chach:** добавить импорт исходного envelope организаторов с сохранением raw timestamps и стабильных message IDs; не подменять ложный `isSuccess` пустым успешным набором. Затем — версии чек-листов и снимки оценок.

**Kroud:** подключить один явно выбранный командой inference provider, передавать весь конфиг критериев, проверять schema и evidence. Вернуть один проверенный результат на RU, KZ и EN. Не начинать обучение модели до работающего baseline.

## Интеграционные проверки

1. N/A исключает разрешённый вес; «Нет» оставляет его. 7 из 10 при весе 15 даёт 10.5 до перераспределения.
2. Новый критерий с новым ID и другой шкалой проходит без изменения исходного кода оценщика.
3. Несуществующее доказательство, дубль/пропуск критерия и ошибочный тип не сохраняются как успешная оценка.
4. Недоступность модели не показывает 100 баллов из демо. `needs_review` не является N/A.
5. Решение по апелляции оставляет исходную оценку, сохраняется после рестарта и пересчитывает итог по исходной версии.
6. Два решения по одной revision дают конфликт вместо потери данных.
7. Ссылка доказательства открывает нужную реплику; для звонка seek используется только при известной привязке времени.
8. За 5 минут команда показывает диалог → объяснение → N/A → апелляцию → новый критерий.

До сквозного сценария не брать дополнительные роли, authentication, сложную аналитику, fine-tuning, декоративные анимации и инфраструктуру масштабирования. Технические улучшения выбирать по фактическим проблемам.
