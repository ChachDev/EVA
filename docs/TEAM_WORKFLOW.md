# Работа без пересечений

Mansur редактирует `frontend/`, Chach — `backend/`, Kroud — `ml/`. Рабочая папка терминала сама по себе не ограничивает доступ ИИ к остальному репозиторию: `AGENTS.md` — инструкция, а не техническая защита.

## Настройка работы людьми

1. Человек сохраняет начальную базу в Git и передаёт её всем участникам. ИИ не выполняет Git-операции.
2. У каждого отдельная локальная рабочая копия, **все работают только в `main`**. Отдельные ветки для задач или участников не создаются. ИИ не создаёт ветки/worktree и не переключает ветку; если текущая ветка не `main`, сообщает человеку и не начинает изменения. Несколько агентов не должны одновременно писать в одну и ту же роль.
3. Открывать чат ИИ с явно указанной ролью и папкой. При наличии настроек sandbox/tool permissions разрешить запись только в свою зону, чтение — в контракты и нужные источники.
4. Не давать ролевому агенту GitHub-инструменты на запись, токены публикации или разрешения deploy. Отключение инструментов даёт более сильную гарантию, чем текстовый запрет.
5. Зависимости/порты/данные раздельные. Человек запускает полный стенд; каждый ИИ запускает только свою часть. После проверки человек сам выполняет commit, обмен изменениями и интеграцию.

## Задача для ИИ

Задавать маленький проверяемый результат: роль, разрешённая папка, конкретный сценарий, вход/выход, критерий готовности. В личных README есть стартовые запросы. Не использовать поручения «поправь всё, чтобы заработало» без границ.

Перед завершением ИИ сообщает: что изменилось, как проверено, что ещё не реализовано. Для read-only проверки границ из корня:

```powershell
python tools/check_scope.py --role frontend
```

Проверка читает локальные изменённые/новые имена файлов; ничего не индексирует, не коммитит и не отправляет. Она не различает авторов общих незакоммиченных файлов. Поэтому запускать в своей рабочей копии после человеческой фиксации базы. Это диагностика, не песочница, не серверная защита и не замена review.

## Если нужен чужой файл или новый контракт

Добавить в свою `CHANGE_REQUESTS.md`: проблему; минимальное изменение; вход/выход и пример; затронутые роли; влияние на совместимость; желаемую проверку. Продолжить независимую работу с текущим контрактом/fixture. Не исправлять соседнюю папку «заодно».

Человек согласует изменение с участниками и поручает отдельную интеграционную задачу с точными общими файлами. После обновления контракта владельцы адаптируют каждый свою часть. Изменения общих схем, fixture и пояснения должны идти вместе. На время интеграции ролевые агенты не редактируют те же файлы.

## Готовность задачи

- Нет записи вне своей папки, изменений `.git/`/GitHub или глобальной среды.
- Соответствие текущим схемам; новые возможности не ломают режимы demo/http.
- Проверен пользовательский сценарий или содержательная бизнес-логика; нет фиктивных успешных результатов.
- README отражает реально работающие команды и оставшиеся ограничения.
- Secrets, DEV, аудио, локальная БД и сырые модельные ответы не попали в передаваемые файлы.

Требование PDF отправить открытый Git-репозиторий организаторам относится к людям. Ни оно, ни внешний skill не отменяют запрет агентам изменять Git/GitHub.
