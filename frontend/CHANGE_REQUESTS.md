## FE-001 — реестр диалогов, метаданные и страницы

**Адресат:** Chach (Backend), человек-интегратор (contracts).
**Статус:** предложено, не согласовано.
**Ответ владельца:** ожидается.

**Сценарий.** Аудитор ищет диалог по тексту, каналу, оператору и дате, открывает его из очереди. Сейчас `GET /api/v1/conversations` возвращает массив с одним примером. `conversation` содержит канал, язык, сообщения и `audio_url`, но не оператора, дату начала, тему, длительность или состояние обработки.

**Предложение, не существующий API:** добавить отдельный список кратких карточек, сохранив старый endpoint:

```text
GET /api/v1/conversation-summaries?limit=25&cursor=...&q=...&channel=voice_call
GET /api/v1/conversations/{conversation_id}
```

Предлагаемые дополнительные фильтры: `operator_id`, `started_from`, `started_to`, `evaluation_status`. Первый ответ — новый DTO с пагинацией; второй — существующий полный `conversation` без изменения его обязательных полей.

```json
{
  "items": [
    {
      "conversation_id": "demo-ru-001",
      "channel": "agent_chat",
      "language": "RU",
      "operator": null,
      "started_at": null,
      "topic": null,
      "duration_seconds": null,
      "processing_status": "ready",
      "latest_evaluation": null
    }
  ],
  "next_cursor": null
}
```

Предлагаемый `operator`: `{ "id": "op-demo-001", "display_name": "Демооператор" }` либо `null`. `started_at` — ISO 8601 с часовым поясом либо `null`; это начало разговора, а не время оценки. `duration_seconds` — длительность аудио либо `null`; её нельзя получать из времени последней реплики. `latest_evaluation` — `{ "id": "eval-demo-001", "status": "needs_review", "total": null }` либо `null`. Состояния обработки `processing`, `ready`, `failed` и их источник нужно подтвердить с Backend; они не описывают качество оценки.

**Совместимость.** Нынешний массив и канонический `conversation` остаются прежними. Для списка нужен отдельный согласованный контракт. Параметры пагинации и ошибок утверждает интегратор; предложение — лимит 1–100, непрозрачный курсор и стабильный порядок без повторов между страницами. Отсутствующие метаданные передаются как `null`.

**Что блокируется:** полноценная очередь, серверные фильтры, карточки с оператором и датой. Импорт — следующий зависимый сценарий; формат файла, ошибки строк и статусы задания этим запросом не утверждаются.

**Что Frontend продолжает:** поиск и фильтр по уже загруженным диалогам, просмотр переписки и доказательств.

**Критерий проверки:** две страницы синтетических данных без дублей, фильтр по каналу, корректное завершение списка, пустой результат, неизвестные метаданные, некорректный курсор и 404 для отсутствующего диалога. Никакие реальные клиентские данные для проверки не нужны.

## FE-002 — выдача аудио и подтверждённая временная привязка

**Адресат:** Chach (Backend), Kroud (ML), человек-интегратор (contracts).
**Статус:** предложено, не согласовано.
**Ответ владельца:** ожидается.

**Сценарий.** Аудитор запускает запись и переходит к реплике. Сейчас есть только `audio_url` и `offset_seconds`; в примере аудио отсутствует. Нельзя трактовать абсолютный `timestamp` как смещение от начала записи.

**Предложение, не существующий API:** согласовать метаданные и выдачу записи через Backend:

```text
GET /api/v1/conversations/{conversation_id}/audio-metadata
GET /api/v1/conversations/{conversation_id}/audio
```

Синтетический пример предлагаемого ответа метаданных:

```json
{
  "conversation_id": "demo-voice-001",
  "availability": "available",
  "stream_path": "/api/v1/conversations/demo-voice-001/audio",
  "content_type": "audio/mpeg",
  "duration_seconds": 393,
  "offset_origin": "audio_start",
  "offset_mapping_status": "verified"
}
```

`availability`: предлагаются `available`, `processing`, `missing`, `forbidden`. При отсутствии разрешённой записи `stream_path`, тип и длительность могут быть `null`. `offset_mapping_status` — `verified` или `unknown`; при `unknown` `offset_origin=null`, непроверенные `messages[].offset_seconds` остаются `null`, а точный переход недоступен. Подтверждённые смещения отсчитываются в секундах от начала именно выдаваемого файла.

Backend определяет допустимый путь и проверяет доступ; Frontend не открывает произвольные внешние `audio_url` автоматически. Для перемотки предлагается поддержка HTTP Range с ответами 206/416 и корректным Content-Type. Допустимые origin остаются явными локальными адресами; внешний аудиохостинг этим предложением не разрешается.

ML должен сообщать, к какой версии аудио привязаны распознанные реплики. Обрезка или замена записи требует новой привязки; нельзя сохранять старые смещения без проверки. Данные для настоящей waveform можно добавить отдельным контрактом позже; случайные полосы её не заменяют.

**Совместимость.** Текущая семантика `offset_seconds` сохраняется. Для метаданных нужен новый DTO; маршруты, типы ошибок и связь с текущим `audio_url` утверждает интегратор.

**Что блокируется:** настоящее воспроизведение, достоверная waveform и синхронизация реплик с записью.

**Что Frontend продолжает:** текстовые переходы к доказательствам и явное состояние «аудио недоступно».

**Критерий проверки:** короткий синтетический файл; запуск только действием пользователя; перемотка к подтверждённому смещению; отсутствие точного seek при `null`; missing/forbidden без подмены демозаписью; ошибки загрузки и Range без падения интерфейса. Проверить, что новая версия записи не использует устаревшие смещения.

## FE-003 — ручная проверка, апелляции и неизменяемые снимки

**Адресат:** Chach (Backend), человек-интегратор (contracts); Kroud (ML) — для отдельного сценария повторной автоматической оценки.
**Статус:** предложено, не согласовано.
**Ответ владельца:** ожидается.

**Сценарий.** Аудитор возвращается к сохранённой оценке, подтверждает её или рассматривает апелляцию. Старое решение, исходная переписка и версия чек-листа должны оставаться доступными.

**Текущий контракт.** `GET /api/v1/evaluations/{id}` уже существует. Запись содержит `original` и `scoring`, но не снимки входного разговора и чек-листа. Нет списка оценок, ручных решений, апелляций и создания версий чек-листа. Нынешний `status=completed` не означает подтверждение человеком.

**Предложение, не существующий API:** отдельная сущность проверки с собственным статусом и ревизией; исходный `evaluation-record` не перезаписывается.

```text
GET  /api/v1/review-cases/{evaluation_id}
POST /api/v1/evaluations/{evaluation_id}/reviews
POST /api/v1/evaluations/{evaluation_id}/appeals
POST /api/v1/appeals/{appeal_id}/decisions
GET  /api/v1/evaluation-snapshots/{snapshot_id}
GET  /api/v1/evaluations?conversation_id=...&cursor=...
POST /api/v1/checklists/{checklist_id}/versions
```

Пример предлагаемой карточки проверки:

```json
{
  "evaluation_id": "eval-demo-001",
  "revision": 1,
  "review_status": "pending",
  "snapshot_id": "snapshot-demo-001",
  "original_evaluation_id": "eval-demo-001",
  "current_evaluation_id": "eval-demo-001",
  "appeals": []
}
```

`review_status` — отдельное поле; предлагаются `pending`, `confirmed`, `appealed`, `resolved`. Перед утверждением нужно согласовать допустимые переходы и связь с `needs_review`. Подтверждение не должно превращать неизвестную оценку в известную без явных решений по критериям.

Пример запроса подтверждения:

```json
{
  "expected_revision": 1,
  "decision": "confirmed",
  "comment": "Проверены обоснования и связанные реплики."
}
```

Пример создания апелляции по критерию:

```json
{
  "expected_revision": 1,
  "criterion_id": "criterion-demo-001",
  "message_ids": ["m0002"],
  "reason": "Прошу повторно проверить указанный фрагмент."
}
```

Пример отклонения апелляции с объяснением:

```json
{
  "expected_revision": 2,
  "decision": "rejected",
  "reason": "Исходный вывод подтверждён указанными доказательствами."
}
```

Принятие апелляции с изменением результата требует отдельного согласованного тела решения: допустимое значение каждого изменяемого критерия, основание и ссылки на сообщения. Frontend не отправляет самостоятельно рассчитанный итог. Backend валидирует значения, пересчитывает баллы и создаёт новую связанную запись; исходная остаётся неизменной. Точный формат такого решения этим черновиком не утверждается.

**Снимки и версии.** Снимок возвращает полные канонические `conversation` и `checklist`, использованные при создании оценки, а не текущие версии справочников. При выпуске чек-листа клиент передаёт `base_version`, новое имя и массив критериев существующего формата; Backend проверяет конфликт и назначает новую версию. Удаление или изменение старого чек-листа не разрушает сохранённые проверки. Для первой версии можно хранить полные снимки; способ хранения определяет Backend.

**Права и конфликты.** Кто может подавать апелляцию, подтверждать и пересматривать оценку, определяется на Backend после согласования ролей. Автор и время события выставляются сервером. Устаревший `expected_revision` должен возвращать конфликт (предлагается 409); повторная отправка не должна создавать дубликаты. Журнал сохраняет причину, автора, время и связь со старым результатом. Идентификаторы критериев и реплик проверяются относительно снимка этой оценки.

**Совместимость.** Существующие `evaluation-record` и GET по ID сохраняются. Новые сущности требуют отдельных схем; расширение или изменение канонического контракта выполняет только интегратор после согласования. Список оценок, снимки, review/appeal и версии можно внедрять этапами; перечень выше не обещает их одновременную готовность.

**Что блокируется:** достоверная история, сохранение подтверждения, реальные апелляции и редактирование версий.

**Что Frontend продолжает:** чтение текущего чек-листа, просмотр результата и доказательств; можно подключить уже существующий GET оценки по ID, не обещая недоступный исторический снимок.

**Критерий проверки:** повторное открытие оценки после публикации нового чек-листа; сохранность исходного результата после апелляции; серверный пересчёт; отказ для чужих message/criterion ID; конфликт двух решений; отказ без прав; повторная отправка без дублей; отсутствие ложного подтверждения для неразрешённых критериев.
