# EVA: план возможностей продукта

Статус: рабочий план Frontend. Приоритеты ниже — предложения, а не утверждённый объём работ. Зависимости от других участников описаны в [CHANGE_REQUESTS.md](CHANGE_REQUESTS.md); новые API ещё не согласованы и не реализованы.

## Текущая рабочая консоль

- Очередь диалогов с поиском и фильтром по каналу. Поиск работает по загруженным данным, а не по всему будущему серверному реестру.
- Просмотр переписки, поиск реплик и переход между совпадениями.
- Проверка по выбранной версии чек-листа; просмотр критериев и их условий без редактора.
- Обоснование оценки рядом с разговором, подсветка нескольких связанных реплик, переход к предыдущему и следующему доказательству.
- Фильтры критериев: все, замечания, нужна проверка.
- Раздельное отображение отсутствующей оценки, неопределённого результата, неприменимости и грубого нарушения.

Деморежим использует синтетический чат и ручную разметку. В текущем примере нет аудио. В HTTP-режиме реальная оценка зависит от готовности ML; заглушка может вернуть «нужна проверка» без итогового балла. Интерфейс не имитирует сохранение ручного подтверждения или апелляции.

| --- | --- | --- |
| 1 | **Реестр и импорт.** Открывать реальные загруженные диалоги, искать по оператору и дате, видеть этап обработки и возвращаться к нужной записи. | Frontend: список, фильтры и состояния. Backend: импорт, хранение, метаданные, серверный поиск и страницы. Контракты согласовать с интегратором. Основа запроса — FE-001; формат импорта требует отдельного согласования. |

| 3 | **Реальная автоматическая оценка.** Получать проверяемые решения по критериям и ссылки на исходные реплики. | ML: оценщик и проверка его качества. Backend: проверка результата, расчёт и сохранение баллов. Frontend: состояния выполнения, ошибки и явная неопределённость. Существующий контракт оценки сохраняется, пока команда не согласует изменения. |
| 4 | **История оценок.** Повторно открыть результат по ссылке вместе с исходным разговором и той версией чек-листа, по которой его проверяли. | Frontend: подключение уже существующего GET оценки по ID. Backend: список оценок и неизменяемые снимки исходных данных. FE-003. |
| 5 | **Ручная проверка и апелляции.** Подтвердить результат или оспорить конкретный критерий, приложить реплики, увидеть решение и историю изменений. | Frontend: формы и сравнение результатов. Backend: права, статусы, хранение, журнал и защита от конфликтующих изменений. ML нужен только для отдельного сценария повторной автопроверки. FE-003. |
| 6 | **Версии чек-листов.** Менять критерии, веса, шкалы и условия неприменимости; публиковать новую версию без изменения старых оценок. | Frontend: редактор. Backend: хранение и публикация версий. Интегратор: согласованные контракты. ML использует переданную версию. FE-003. |
| Позже | **Аналитика.** Видеть частые замечания и динамику по операторам, командам и периодам. | Нужны реестр с метаданными, накопленные оценки и согласованные серверные агрегаты. Не строить продуктовые выводы на единственном демопримере. |

## Общие правила развития

- Итоговые баллы рассчитывает Backend; Frontend отображает их без повторного расчёта.
- Аудиодорожка строится по реальной записи. Если аудио или привязки нет, показываем это явно; точный переход по времени недоступен.
- Данные об операторе, теме, дате и длительности появляются в рабочем интерфейсе только после получения из согласованного источника.
- Ручное решение и апелляция сохраняют исходную автоматическую оценку. Новая версия чек-листа не изменяет прошлые результаты.
- До работы нескольких пользователей необходимы согласованные идентификация и права доступа; локальный интерфейс не заменяет их.
