# Запросы norerade на общие изменения

Этот файл — локальная очередь для обсуждения с людьми. Общие файлы меняют их владельцы.

## ML-001 · Формулировка критерия управления диалогом

Предложено команде. На странице 2 исходного чек-листа порог первой реакции в три минуты, теги и вложения перечислены как исключённые из оценки. В `contracts/examples/checklist.json` фраза о трёх минутах допускает противоположное прочтение. Привести текст критерия к PDF. Проверка совместимости — если изменились только таймстампы первой реакции, балл по этой причине не снижается. Явное ожидание без предупреждения по-прежнему можно учитывать. В диагностике ML используется локальная конфигурация с точной формулировкой.

## ML-002 · Флаг сомнения при выставленной оценке

Предложено команде, если принимается отображение уверенности. Для спорной оценки, у которой есть конкретное обоснование и допустимое значение, согласовать необязательный флаг низкой уверенности в результате ML, его сохранение Backend и отображение в карточке Frontend. Отдельно сохранить существующее поведение для технической ошибки и действительной нехватки оснований. Проверка совместимости — прежний ответ без флага остаётся валидным, а спорное выставленное значение участвует в обычном расчёте. До согласования флаги доступны только в локальном эксперименте.

Если ML нужны изменения в `contracts/`, API Backend, UI или корневой инфраструктуре, добавь запись сюда и продолжай независимую работу внутри `ml/`.

## ML-003 · Контракт и проверка для ML-002 (уверенность вместе с оценкой)

Кому: владельцы contracts, Chach (Backend), Mansur (Frontend). Предлагается совместимая миграция производителей и читателей: добавить необязательное поле `criteria[].confidence: "low" | "normal"` в новой редакции схемы ответа. В действующей v1 его запрещает `additionalProperties: false`. Отсутствие поля означает «не передано». Сохранять его в `original.criteria` и отображать «Низкая уверенность» рядом с конкретной оценкой, не меняя её веса или балла. Поле `criteria[].status="needs_review"` уже есть и доходит до списка критериев и фильтра интерфейса; оно по-прежнему означает, что оценка отсутствует. Проверить чтение старой записи без поля, сохранение новой записи со scored + low и тем же баллом, и needs_review + null с видимой причиной.

## ML-004 · Нужен ли план сразу при сохранении?

Кому: Chach и владелец контракта. Сейчас публикация сохраняет неизменяемую версию, а ML впервые видит её в запросе оценки. Если редактору нужен признак готовности до первого чата, согласовать внутренний вызов подготовки **после успешного сохранения**: передавать ровно опубликованный снимок и принимать отпечаток плана. Повтор подготовки той же версии должен быть идемпотентным; недоступность ML не должна незаметно откатывать сохранённую версию или выдавать старый план как готовый. Для проверки замены через существующий API эта доработка не требуется.
