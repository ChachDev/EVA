# Chach · Backend

**Все работают только в `main`.** ИИ не создаёт новые ветки (включая `codex/*`), не создаёт worktree и не переключает ветку. Перед правками проверяет текущую ветку через read-only `git status --short --branch`; если это не `main` или detached HEAD, сообщает человеку и не начинает изменения. Разделение работы — по папкам, не по веткам.

Твоя зона — `backend/`: API, хранение оценок, проверка контрактов и детерминированный подсчёт результата. Это рабочая локальная база для разделения команды; данные сейчас только синтетические.

## Быстрый старт

Из корня проекта в PowerShell:

```powershell
cd backend
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --reload
```

API: http://127.0.0.1:8000, документация: http://127.0.0.1:8000/docs. ML коллеги запускается отдельно на http://127.0.0.1:8001. Без него health и списки примеров доступны, создание оценки вернёт 503.

Настройки читаются из переменных окружения. `.env.example` служит справочником и автоматически не загружается:

```powershell
$env:ML_URL = 'http://127.0.0.1:8001'
$env:ML_TIMEOUT_SECONDS = '20'
$env:CORS_ORIGINS = 'http://localhost:5173,http://127.0.0.1:5173'
```

В этой базе ML_URL и CORS допускают только явные локальные HTTP-адреса. HTTP proxy из окружения не используется, redirect от ML не выполняется. Слушай только `127.0.0.1`: аутентификация пока не реализована.

## Что готово

| Метод и адрес | Результат |
| --- | --- |
| `GET /health` | Проверка самого backend; не обещает доступность ML |
| `GET /api/v1/checklists` | Массив с синтетическим `contracts/examples/checklist.json` |
| `GET /api/v1/conversations` | Массив с синтетическим `contracts/examples/conversation.json` |
| `POST /api/v1/evaluations` | Проверка данных, вызов ML, подсчёт, сохранение; HTTP 201 |
| `GET /api/v1/evaluations/{id}` | Сохранённая оценка, включая неизменённый `original` |

Тело создания:

```json
{"conversation_id":"demo-ru-001","checklist_id":"freedom-cqa","checklist_version":1}
```

Ответ содержит `id`, `status`, UTC `created_at`, `original` и `scoring`, как в `contracts/schemas/evaluation-record.schema.json`. `status=completed` означает рассчитанный результат; pending или отсутствие применимого веса дают `needs_review`.

Внутренний вызов — `POST http://127.0.0.1:8001/v1/evaluate` с `schema_version=1.0.0`, полной беседой и выбранной версией чек-листа. Таймаут/ошибка ML → 503; невалидный ML JSON, значения или evidence → 502. В обоих случаях оценка не сохраняется. Неизвестный ID → 404, несовпадающая версия чек-листа → 409, некорректное тело → 422.

SQLite находится в `backend/data/eva.sqlite3` и создаётся при запуске. Каждый вызов создаёт отдельную неизменяемую запись; после перезапуска её можно получить по ID. `original` не перезаписывается; апелляции пока не реализованы. База и виртуальное окружение исключены из Git локальным `.gitignore`.

## Границы кода

- `app/main.py` — HTTP API и сборка приложения.
- `app/contracts.py` — JSON Schema Draft 2020-12, локальный registry `$id`, проверки соответствия IDs, типов и evidence. Схемы читаются из `contracts/`, без сетевого обращения к `eva.local`.
- `app/scoring.py` — чистая функция подсчёта, без HTTP, БД и ML.
- `app/ml_client.py` — локальный HTTP-клиент с таймаутом.
- `app/storage.py` — SQLite и сохранение полного envelope.
- `tests/` — предметные проверки scoring, контрактов, ошибок ML и сохранения после перезапуска.

## Как считается балл

`ratio = 1 или 0` для boolean; `ratio = value / max(scale)` для scale. Для шестого критерия шкала заканчивается на 10, а вес равен 15: значение 7 даёт 10.5 исходных взвешенных баллов.

`total = 100 × Σ(ratio × weight) / Σ(applicable weight)`.

NA допустимо только при `allow_na=true`, `status=scored`, `value=null` и evidence исключительно вида `not_applicable`. Смеси с другими видами доказательств отклоняются. Этот критерий исключается из знаменателя; его `points` и `effective_weight` равны null. `needs_review` означает неизвестное решение и требует проверки, а не NA.

Доказательства должны соответствовать статусу: `scored` не допускает `uncertain`, даже в смеси с `not_applicable`. Для `needs_review` каждое доказательство имеет только вид `uncertain`; смеси с `message`, `missing_action` и `not_applicable` отклоняются до подсчёта и сохранения.

Для полного результата `criteria.points = 100 × ratio × weight / applicable_weight`; `effective_weight = 100 × weight / applicable_weight`. Это нормализованные вклады в итог из 100. Флаги имеют нулевой вес и нулевые вклады; подтверждённая грубая ошибка выставляет `has_gross_error=true`, но не обнуляет итог автоматически.

При любом pending `status=needs_review`, `total=null`; нормализованные вклады всех взвешенных критериев также null, чтобы не показывать неполный результат как окончательный. `applicable_weight` в этом случае — только сумма уже определённых применимых весов, не окончательный знаменатель. Неопределённый флаг даёт `has_gross_error=null`, если другой флаг не подтвердил нарушение. Когда все взвешенные критерии NA или имеют вес 0, результат `not_calculable`, итог null.

Секции нормируются отдельно до 100 внутри своей секции. Секция с pending или нулевой суммой применимых весов имеет `score=null`; поэтому секция `violations` не получает фиктивный численный балл. Критерии с `section_id=null` участвуют в общем итоге, но не образуют секцию.

Расчёты используют Decimal; итог, секция и каждый отображаемый вклад округляются только в конце до двух знаков по ROUND_HALF_UP. Итог не суммирует уже округлённые отображаемые вклады; их сумма может отличаться на 0.01 из-за округления.

## Проверки

```powershell
.\.venv\Scripts\python.exe -m pytest
```

Тесты используют только синтетические root fixtures, отдельные базы в `backend/tests/.tmp/` и HTTP mocks. Они проверяют NA, шкалу/вес, flags, Decimal rounding, pending, bool против числа, набор критериев, evidence IDs, 503/502 и чтение после перезапуска. Direct dependencies закреплены точными версиями; это не полный lockfile транзитивных зависимостей.

## Следующие независимые задачи Chach

1. Импорт реального DEV-набора из разрешённого командой URL в локальную `backend/data/`, затем в БД с source metadata и неизменяемыми IDs. Приёмка: исходные каналы и transcript нормализуются по контракту, повторный импорт предсказуем, ошибки видны, реальные данные не попадают в fixtures/Git или сторонние сервисы. Для тестов адаптера использовать синтетические примеры. Автоматического скачивания в текущей базе нет.
2. Версионирование чек-листов и CRUD после общего согласования контрактов. Приёмка: старая оценка всегда ссылается на исходную версию, weights/scale/NA валидируются до сохранения.
3. Апелляции и ручное решение отдельной сущностью. Приёмка: есть автор, время и причина, оригинальный ML ответ не меняется, пересчёт использует ту же scoring-функцию.
4. Опциональная очередь, только если измеренная задержка ML не укладывается в согласованный HTTP-таймаут. Сначала согласовать необходимость с Frontend и ML; затем добавить идемпотентность и статусы исполнения. Приёмка: повторный запрос не дублирует работу, сбои не дают ложный успех. Для локального демо очередь не обязательна.
5. Аутентификация и разграничение доступа — отдельная задача перед общим сетевым развёртыванием. Для текущего локального демо это не обязательный этап; сервер остаётся на loopback.

Не меняй общие контракты в одиночку: создай запись в `CHANGE_REQUESTS.md`, договорись с владельцами и дождись интеграции человеком.

## Правила для твоего ИИ

Дай ИИ `AGENTS.md` из корня, этот README и `backend/AGENTS.md`. Разрешена запись только в `backend/**`; чужие роли и общие файлы не трогать. Никаких git-изменений, GitHub, commit/push, PR, issue, Actions, deploy и публикации. ИИ готовит локальную работу и отчёт проверок; интеграцию выполняет человек. Эти текстовые правила не заменяют отдельный sandbox или checkout.

```text
Я Chach, владелец Backend. Прочитай AGENTS.md, contracts/README.md,

При необходимости изменить чужую зону запиши предложение в

```
