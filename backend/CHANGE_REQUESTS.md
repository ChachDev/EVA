# Запросы Backend к другим владельцам

## 2026-11-07 · Chach · Контракты следующих backend-сценариев

Статус: одобрено пользователем и реализовано в текущем backend-пакете. Новые общие схемы и примеры разрешены явно; точные маршруты приведены ниже и в `contracts/README.md`. Подключение Frontend остаётся у Mansur. Ниже сохранено обоснование первоначального предложения.

- Владелец: общий контракт + Frontend; ML проверяет совместимость формата evidence.
- Сейчас backend хранит разговоры, immutable checklist versions и request snapshots. Существующий `evaluation-record` v1 остаётся без новых полей.
- Для редактора нужен общий запрос создания новой версии чек-листа, правило выбора версии в списке и ошибки конфликтующей версии. Редактирование не должно менять уже сохранённую версию.
- Для апелляции нужны схемы создания обращения по `evaluation_id + criterion_id`, решения проверяющего с reason/evidence/author и чтения original/decisions/final. Названия endpoint пока не закрепляются.
- Решение должно содержать `expected_revision`; два решения по одной revision дают один успех и один 409. Original и snapshots сохраняются, final пересчитывается по исходному чек-листу.
- Нужен отдельный способ чтения снимка разговора старой оценки и списка сохранённых оценок без самовольного расширения `evaluation-record` с `additionalProperties=false`.
- Для импорта сейчас используется явная локальная CLI-команда. UI-импорт требует общего запроса/ответа, правила полного набора/pagination и решения, глобально ли уникален `conversation_id` между группами. Пока изменённое содержимое или другая группа под тем же ID отклоняются целиком.
- Проверки: JSON Schema fixtures; новая версия не меняет старую оценку; invalid evidence/value отклоняются; решения переживают restart; stale revision даёт 409; frontend показывает original и final раздельно.
- Решение человека: реализовать новые API, разрешить связанные `contracts/schemas/**`, `contracts/examples/**`, `contracts/README.md`. Backend реализован; проверка настоящего ML/ASR и Frontend выполняются отдельно.

## 2026-11-07 · Chach · Аудит стыковки ML_V1

Статус: исторический аудит `98c3d51` (ML_V1) и `dbf49db` (переименование владельца ML). Модель и benchmark-скрипты не запускались; это аудит исходников и контрактов, а не подтверждение качества или скорости модели. В `afa33aa` уже есть ISSAI-адаптер `/v1/evaluate` и поддержка нового чек-листа; прежнее описание stub ниже относится к старой ревизии. Диагностика, история, snapshots и пересмотр реализованы новым backend-пакетом. Вопросы реального runtime и воспроизводимости остаются.

- Владелец: norerade — ML runtime и эксперименты; команда — общие схемы; Mansur — отображение состояния и согласование ожидания ответа.
- **Адаптер и порт.** Рабочий `ml/eva_ml/app.py` по-прежнему вызывает stub. `ml/benchmarks/local_compare.py` запускает llama-server на том же 8001, но обращается к `/v1/chat/completions`; Backend вызывает `/v1/evaluate`. Для подключения нужен ML-адаптер существующего контракта и отдельный согласованный loopback-порт движка. Проверки: wrapper и движок запускаются одновременно; API возвращает реальный provider/model; ошибка модели не превращается в успешную оценку.
- **Канонический результат.** Эксперимент возвращает словарь критериев со строками `true`, `false`, `N/A`, `review`, а общий ответ требует типизированные значения, status, identity и структурированный evidence. Преобразование и выбор `message`/`missing_action` принадлежат ML, Backend проверяет готовый результат. Проверки на synthetic fixtures: корректный ответ проходит, неизвестный ID, недопустимое значение и неверный evidence отклоняются; неопределённость остаётся `needs_review`.
- **Произвольный чек-лист.** `frozen_facts.py` выбирает таблицу по title, проверяет type/scale/na_condition, но не входную instruction; затем подставляет локальную rubric_instruction. Это допустимо как фиксированный эксперимент, но не как реализация будущего редактора. Нужны обработка переданной инструкции либо явный отказ от неподдерживаемой версии/хеша. Проверки: новая instruction при прежнем title меняет оценивание либо даёт явную ошибку; новый критерий не приводит к скрытому использованию старых правил.
- **Время и параллельность.** Сейчас Backend ограничивает всю ML-операцию 20 секундами, Frontend ждёт 30 секунд; benchmark допускает 300 секунд на отдельный вызов и несколько последовательных стадий, движок запускается с `-np 1`. Это разные бюджеты, а не измеренная задержка. Нужны замеры выбранной модели, p95, поведение отмены и согласование числа одновременных запросов. Если синхронного бюджета недостаточно, отдельно согласовать контракт долговечных заданий и опроса состояния; простое увеличение timeout не заменяет очередь и восстановление после restart.
- **ML-002 / низкая уверенность.** Не добавлять флаг в ответ v1 до согласования: `additionalProperties=false` отклонит его и на уровне ответа, и внутри критерия. Нужны версия/порядок обновления потребителей и fixtures для старого/нового ответов. Сомнение при допустимой оценке, отсутствие оснований и техническая ошибка должны оставаться разными состояниями. Для ML-001 уточнение инструкции следует сохранить отдельной immutable-версией, если команда меняет опубликованный чек-лист.
- **Воспроизводимость.** В identity `frozen_facts.py` нет digest содержимого GGUF, бинарника и импортированных обработчиков `ask`/`engine`; замена по прежнему пути может смешать результаты при resume. В `evidence_gate_check.py` текущий набор сверяется с родителем только по ID: изменение реплик под прежними ID не обнаруживается. Нужны хеши модели/runtime/протокола/входов и отказ от resume при несовпадении. Backend потребуется согласованный источник этих метаданных, чтобы сохранять происхождение оценки и длительности попыток без текстов диалогов в логах. Ошибки и неизвестное usage не должны считаться нулевой стоимостью.
- **Зависимости эксперимента.** `local_compare.py` импортирует `openpyxl`, которого нет в объявленных ML requirements. Владелец ML определяет отдельные benchmark-зависимости и инструкции запуска; Backend не устанавливает их в своей среде.

Первоначальный план: диагностика готовности ML и различение ошибок → список/детали истории с исходными snapshots → учёт попыток и метаданных исполнения. Первые два пункта реализованы текущим backend-пакетом. Долговечные задания оценки — после замера runtime и согласования схем. Формулу баллов не менять под результаты эксперимента.

Проверки Backend на этой ревизии: 199 основных тестов и 6 отдельных PostgreSQL-тестов прошли; зависимости согласованы. Synthetic-проверка подтверждает: канонический ответ v1 принимается, raw benchmark-ответ и добавленный low_confidence отклоняются. Сквозная оценка реальной моделью, качество RU/KZ/EN и latency не проверялись.

На момент исторического аудита общие схемы, Frontend и ML не изменялись. Текущий статус согласованного пакета приведён ниже.

## 2026-11-07 · Chach · Новые сценарии и пакет интеграции API

Основание: пользователь подтвердил три входа — готовые транскрипты организаторов, загрузка новых аудиозаписей с локальным распознаванием, загрузка/ручной ввод переписки клиента с оператором для оценки. Ответы клиентам от чат-бота не входят в задачу.

Аудит `afa33aa`: ML теперь имеет реальный ISSAI-адаптер `/v1/evaluate`, отдельный локальный порт движка и обработку изменённого чек-листа. Прежнее заключение о stub описывало `dbf49db`, а не эту ревизию. Frontend продолжает использовать прежние пять HTTP-сценариев; FE-001–003 остаются предложениями. ASR-провайдера и `/v1/transcribe` в ML нет.

Статус: пользователь одобрил реализацию и явно разрешил общие схемы, примеры и README контрактов. Пакет реализован; новые HTTP-маршруты и 11 пар schema/example доступны в текущих файлах. Существующие успешные v1-форматы сохранены. Это backend-интеграция, не подтверждение готовности UI или настоящего ASR.

Реализованный пакет API:

| Сценарий | Запрос | Ответ / правила |
|---|---|---|
| Ввод переписки/готового транскрипта | `POST /api/v1/conversations`, operation_id, channel, language, messages без ID | Канонический conversation; сервер назначает детерминированный ID разговора/реплик. Ссылки аудио не скачиваются |
| Чтение диалога | `GET /api/v1/conversations/{id}` | Канонический conversation или 404 |
| Публикация чек-листа | `POST /api/v1/checklists/{id}/versions`, base_version, name, criteria | Канонический checklist с новой версией; stale base — 409, старые версии неизменны |
| История | `GET /api/v1/evaluations?conversation_id=...&limit=...&cursor=...` | items канонических records, next_cursor; стабильный порядок, limit 1–100 |
| Исходные данные оценки | `GET /api/v1/evaluations/{id}/snapshot` | Канонический evaluation-request; для legacy без снимка явная недоступность |
| Апелляция | `POST /api/v1/evaluations/{id}/appeals`, operation_id, expected_revision, criterion_id, reason, message_ids | Сохранённая апелляция; IDs проверяются относительно исходного снимка |
| Решение проверяющего | `POST /api/v1/appeals/{id}/decisions`, operation_id, expected_revision, decision, reason, optional criterion override | rejected сохраняет текущий вывод, accepted требует валидное значение и evidence. Итог рассчитывает Backend |
| Проверка и итог | `GET /api/v1/review-cases/{evaluation_id}` | revision, original, appeals, decisions, final; original неизменен, final — отдельная проекция |
| Загрузка записи | `POST /api/v1/audio-assets`, raw аудио с MIME и UUID Idempotency-Key | audio-asset с id, размером/хешем/MIME; файл в backend/data, без использования имени клиента как пути |
| Воспроизведение | `GET /api/v1/audio-assets/{id}/content` | Локальная запись с Range 206/416; никакого автоматического внешнего прокси |
| Запрос распознавания | `POST /api/v1/transcriptions`, asset_id, language, operation_id | Сохранённое задание; статусы queued/running/completed/failed/needs_review |
| Чтение задания | `GET /api/v1/transcriptions/{id}` | Состояние, ошибка без содержимого файла, conversation_id только после валидного результата |
| Метаданные записи | `GET /api/v1/audio-assets/{id}` | audio-asset без внутреннего пути |
| Подтверждение ролей | `POST /api/v1/transcriptions/{id}/review`, operation_id, roles | client/operator для всех сегментов; unknown не угадывается автоматически |

Общие правила: существующие схемы v1 и успешные ответы остаются прежними; новые запросы/ответы получают отдельные схемы. В локальном demo автор решения задаётся серверной конфигурацией и не выдаётся за аутентифицированного пользователя. Повторы operation_id возвращают прежний результат только при том же содержимом; другое содержимое — 409. Два решения с одной revision не могут оба пройти. Незавершённое/ошибочное распознавание не создаёт фиктивный текст или оценку.

Для ASR остаётся решение ML-владельца о настоящем локальном провайдере и проверка качества RU/KZ/EN/ролей. Backend хранит/выдаёт файл, управляет заданием и валидирует транскрипт; Frontend добавляет upload, прогресс, плеер и проверку реплик. Неизвестный speaker переводит job в needs_review; после явного подтверждения всех ролей создаётся разговор. Wire-контракт уже описан в `contracts/README.md`: loopback `POST /v1/transcribe`, multipart `file`, `language`, `audio_sha256` → JSON `transcription-result`, привязанный к хешу и языку. Runtime отвергает stub/mock/fixture/demo. В ML такого endpoint сейчас нет; ASR_URL по умолчанию пуст, upload работает отдельно, создание job даёт 503. Synthetic transport tests не выдаются за реальное распознавание.

Разрешение на интеграционную задачу в `contracts/schemas/**`, `contracts/examples/**`, `contracts/README.md` получено; пакет реализован. Frontend и ML исходники остаются у владельцев. Осталось подключить FE-сценарии, реальный ASR и проверить задержки реальной модели. Текущие лимиты: 1 активная ML-оценка + 4 ожидающих запроса на процесс, общий ML-бюджет 20 секунд против FE 30 секунд, JSON 1 MiB, raw audio 25 MiB. Для локальной модели используйте один uvicorn worker; несколько процессов умножают inference/ASR concurrency.

Дополнительное исправление ML: в `eva_ml/issai.py` table_for считает шкалы [0,5,20] и [0.0,5.0,20.0] равными, но contract_row сравнивает строковые представления и может получить StopIteration для допустимой числовой ступени. Требуется числовое сравнение и тест; Backend не должен незаметно переписывать чек-лист ради обхода.

Критерии приёмки: synthetic integration tests; immutable versions/snapshots; повторные запросы без дублей; конкурентный конфликт; серверный пересчёт апелляции; ограничения размера/типа файла и JSON; безопасные ошибки; restart заданий; настоящий ASR отдельно подтверждается реальным локальным провайдером, не тестовой фикстурой.

Текущее безопасное наблюдение: audit-data подтвердил 65 разговоров / 1268 сообщений, 60 agent_chat + 5 voice_call, RU 35 / KZ 15 / EN 15, 5 аудиоссылок и 1 валидную версию чек-листа. Doctor: DB ready, ML unavailable. Это не оценка моделью и не проверка аудиофайлов. Подробности новых API, миграций и ограничений — в `backend/README.md`.
